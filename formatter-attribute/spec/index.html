Abstract

This specification extends HTML with a formatter content attribute for input and select elements. The attribute is a template, such as ({value}), that the user agent applies to the control’s value when the form is submitted. The user still sees and edits the plain value, validation still checks the plain value, and the server receives the formatted one, without script.

1. Introduction

This section is non-normative.

Servers often expect a value in a format that is awkward for users to type: a telephone area code in parentheses, an amount with its currency code, a country calling code with a leading +. Today authors either make the user type the extra characters, which invites mistakes and needs looser validation, or add script that rewrites the value before the form is submitted.

The formatter attribute lets authors declare the submitted format instead. The user types only the part that varies, and the user agent adds the rest when the form is submitted.

<form action="/register">
  <label>Area code
    <input type="tel" name="areaCode" maxlength="3" pattern="[0-9]{3}"
           formatter="({value})">
  </label>
  <button>Register</button>
</form>

The user types 206. The field shows 206, the pattern attribute checks 206, and value returns "206". Submitting the form sends:

areaCode=(206)

If the user leaves the field blank, the form sends areaCode=, not areaCode=().

User agents that don’t support this specification ignore the attribute and submit the plain value, areaCode=206.

2. The formatter attribute

2.1. Formattable elements

A formattable element is either:

  • an input element whose type attribute is in a state whose value mode is value; or

  • a select element.

Note: The states whose value mode is value are Text, Search, Telephone, URL, Email, Password, Date, Month, Week, Time, Local Date and Time, Number, Range, and Color. Checkboxes, radio buttons, file uploads, hidden inputs, and buttons submit values that the author already controls with the value attribute, so they have no need for a formatter.

2.2. The content attribute

The formatter content attribute is a template for the value that the control submits. It can be specified on input and select elements. It must only be specified on formattable elements. On any other input element, the attribute does not apply and has no effect.

The template is made up of literal text and the value placeholder, {value}, which stands for the control’s value. The value placeholder can appear any number of times, including not at all. To include a literal U+007B ({) or U+007D (}) in the submitted value, authors write it twice: {{ or }}.

With a control whose value is 206:
formatter Submitted value
({value}) (206)
{{{value}}} {206}
{{value}} {value}
{value}-{value} 206-206

If present, the attribute’s value must be a valid formatter template: a string that, when parsed, never reaches an unmatched brace, and in which every placeholder is {value}.

To parse a formatter template given a string input, run these steps. They return a list whose items are either strings, which are literal text, or the special value placeholder.

  1. Let tokens be an empty list.

  2. Let literal be the empty string.

  3. Let position be a position variable for input, initially pointing at the start of input.

  4. While position is not past the end of input:

    1. Let c be the code point at position within input.

    2. If c is U+007B ({) or U+007D (}), and the code point after position is also c, then append c to literal, advance position by 2, and continue.

    3. If c is U+007B ({), then:

      1. Let start be position.

      2. Advance position by 1.

      3. Let identifier be the result of collecting a sequence of code points that are neither U+007B ({) nor U+007D (}) from input, given position.

      4. If identifier is not the empty string, and position is not past the end of input, and the code point at position is U+007D (}), then:

        1. If literal is not the empty string, then append literal to tokens, and set literal to the empty string.

        2. If identifier is "value", then append placeholder to tokens. Otherwise, the placeholder is replaced with nothing.

        3. Advance position by 1.

        4. Continue.

      5. Unmatched brace: Set position to start.

    4. Append c to literal, and advance position by 1. If c is U+007B ({) or U+007D (}), this is also an unmatched brace.

  5. If literal is not the empty string, then append literal to tokens.

  6. Return tokens.

Note: User agents are lenient with invalid templates. A brace that is neither doubled nor part of a placeholder is kept as literal text, and a placeholder other than {value}, such as {Value}, is replaced with nothing.

To format a value given a formattable element element and a string value:

  1. If element does not have a formatter attribute, or value is the empty string, then return value.

  2. Let result be the empty string.

  3. For each token of the result of parsing the value of element’s formatter attribute:

    1. If token is placeholder, then append value to result.

    2. Otherwise, append token to result.

  4. Return result.

Note: Empty values are never formatted, so an optional field that the user leaves blank doesn’t submit the template’s literal text.

2.3. The IDL attribute

interface mixin FormatterAttribute {
  [CEReactions, Reflect] attribute DOMString formatter;
};
HTMLInputElement includes FormatterAttribute;
HTMLSelectElement includes FormatterAttribute;

The formatter IDL attribute must reflect the formatter content attribute.

const areaCode = form.elements.areaCode;

areaCode.value;                         // "206"
areaCode.formatter;                     // "({value})"
new FormData(form).get("areaCode");     // "(206)"

// Feature detection.
const supported = "formatter" in HTMLInputElement.prototype;

3. Form submission

3.1. Changes to constructing the entry list

The algorithm for constructing the entry list [HTML] is changed as follows. Inserted text is

marked like this and removed text is marked like this . Steps that don’t change are summarized in brackets.

  1. For each element field in controls, in tree order:

    1. [The steps up to and including "Let name be the value of the field element’s name attribute" are unchanged.]

    2. If the field element is a select element, then for each option element in the select element’s list of options whose selectedness is true and that is not disabled, create an entry with name and the

      result of formatting, given field and the value of the option element, and append it to entry list.

    3. [The steps for checkboxes, radio buttons, file uploads, and _charset_ are unchanged.]

    4. Otherwise, create an entry with name and the value of the field element the result of formatting field’s value, given field, if field is a formattable element, or the value of field otherwise , and append it to entry list.

    5. [If the element has a dirname attribute, then append its directionality entry. This step is unchanged.]

Note: FormData’s constructor and the formdata event use the same algorithm. Scripts calling new FormData(form) therefore see the formatted value, exactly as the server does.

3.2. Interaction with other features

This section is non-normative.

What the user sees

The formatter attribute doesn’t change what the control displays or what the user edits.

value

The IDL attribute keeps returning the plain value. Only form submission sees the formatted value.

Constraint validation

required, pattern, minlength, maxlength, and every other constraint check the plain value.

dirname

The directionality entry is unchanged.

select elements with multiple

Each selected option’s value is formatted on its own, and each becomes its own entry.

Autofill

Autofill fills the plain value, as it does today. The formatter applies when the form is submitted.

4. Changes to the HTML Standard

To integrate this specification into the HTML Standard [HTML], make these changes:

  1. In the input element:

    • Add formatter to the element’s content attributes.

    • Add HTMLInputElement includes FormatterAttribute; to the DOM interface.

    • Add a formatter row to the table that summarizes which content attributes apply to each type state. Mark it "Yes" for every state whose value mode is value, and not applicable for every other state.

  2. In the select element, add formatter to the element’s content attributes, and HTMLSelectElement includes FormatterAttribute; to the DOM interface.

  3. Add the definitions in § 2 The formatter attribute as a new subsection of "Attributes common to form controls".

  4. Apply the change in § 3.1 Changes to constructing the entry list.

  5. In the index of element attributes, add a row: attribute formatter; elements input, select; description "Template for the submitted value"; value "Text".

5. Accessibility considerations

The formatted value is never shown to the user. If the format matters to the user, for example because they will see it later in a confirmation email, authors should describe it in the control’s label or nearby text.

Because the user no longer types the fixed characters, fields can use simpler input modes, such as inputmode="numeric", and simpler instructions. This helps users of on-screen keyboards, voice input, and switch access.

6. Security and privacy considerations

  • This specification exposes no new information. The formatted value contains only the control’s value and text the author wrote.

  • The formatter attribute is plain text substitution. It can’t run script, fetch resources, or evaluate expressions.

  • Servers must not rely on the formatter for security. User agents without support, and clients that aren’t browsers, submit whatever values they like.

7. More examples

This section is non-normative.

A formatter on a select element adds the + to a country calling code, so the option values stay plain numbers. 
<select name="country" formatter="+{value}">
  <option value="1">United States (+1)</option>
  <option value="44">United Kingdom (+44)</option>
</select>

Choosing United Kingdom submits country=+44.

The user types an amount, and the server receives it with its currency. 
<label>Amount (US dollars)
  <input type="number" name="amount" min="1" step="0.01" formatter="{value} USD">
</label>

Typing 25.50 submits amount=25.50 USD. The min and step attributes check the number the user typed.

With multiple, each selected value is formatted separately. 
<select name="tags" multiple formatter="tag:{value}">
  <option>news</option>
  <option>sports</option>
  <option>weather</option>
</select>

Selecting "news" and "weather" submits tags=tag:news&tags=tag:weather.

8. Alternate proposals

This section is non-normative.

8.1. The collector element

The Collector Element proposes a collector element whose pattern attribute uses the same template syntax to combine several controls into one submitted value. A collector around a single control can do the same job as a formatter:

<collector name="areaCode" pattern="({digits})">
  <input type="tel" name="digits" maxlength="3">
</collector>

The formatter attribute is lighter for the common case of one control, needs no extra element, and keeps the control’s own name. The two could be combined, for example by letting a formatted control inside a collector contribute its formatted value.

8.2. Script

Authors can already rewrite values in a formdata event listener. That works for new FormData(form) and for navigation, but it has to be written for each form, and it doesn’t run when script is turned off.

9. Open issues

Attribute name. Alternatives include format, submitformat, and valueformat.

Empty values. Empty values are never formatted. Should authors be able to format them too, for example to send a default?

Transformations. Should the template support simple transformations, such as {value:upper}, trimming, or padding with zeros to a fixed length?

Reading the formatted value. Should there be a read-only formattedValue IDL attribute, so scripts can show the user what will be submitted without building a FormData object?

More controls. Should textarea elements, and input elements in the Hidden state, accept formatter? Should form-associated custom elements be able to opt in?
