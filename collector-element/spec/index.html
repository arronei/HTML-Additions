Abstract

This specification extends HTML with a collector element. A collector groups the input and select elements that hold the pieces of one value, such as the parts of a telephone number or a date. Its pattern attribute is a template that says how the pieces combine, for example ({areaCode}) {centralOfficeCode}-{lineNumber}. The collector submits the combined value under its own name, and it is validated as a whole: it is invalid while the pattern is only partly filled in, or while any of its pieces is invalid, and it reports one error message for the whole value.

1. Introduction

This section is non-normative.

Many forms collect a single value through several controls: a telephone number split into area code, central office code, and line number; a date entered as a day, a month picked from a list, and a year; a card expiry date in two select elements. Each of these forms currently needs script to:

  • combine the pieces into the one string the server expects, usually by copying them into a hidden field;

  • add the separators that belong between the pieces, such as the parentheses and hyphen of a telephone number;

  • check that the value is complete, and not just that each piece is valid on its own; and

  • show one error message for the whole value, instead of one for each piece.

The collector element lets authors declare the value instead, and leaves the combining and validating to the user agent.

A form asks for a North American telephone number in three parts: 
<form action="/register">
  <label for="phone">Phone number</label>
  <collector id="phone" name="phone" required
             pattern="({areaCode}) {centralOfficeCode}-{lineNumber}">
    (<input type="tel" name="areaCode" minlength="3" maxlength="3"
            autocomplete="tel-area-code" aria-label="Area code">)
    <input type="tel" name="centralOfficeCode" minlength="3" maxlength="3"
           autocomplete="tel-local-prefix" aria-label="Central office code">
    -
    <input type="tel" name="lineNumber" minlength="4" maxlength="4"
           autocomplete="tel-local-suffix" aria-label="Line number">
  </collector>
  <button>Register</button>
</form>

The user types 206, 555, and 0123. Submitting the form sends one entry:

phone=(206) 555-0123

The three input elements aren’t submitted on their own. As the user fills in the fields, the collector’s value and validity change like this:

areaCode centralOfficeCode lineNumber value Validity
(empty string) valueMissing, because the collector is required
206 (206) - patternMismatch, because the pattern is only partly filled in
206 555 01 (206) 555-01 tooShort, rolled up from lineNumber
206 555 0123 (206) 555-0123 Valid

If the user submits the form too early, the user agent shows one message for the phone number, such as "Please fill out all parts of this field", and moves focus to the first empty part.

User agents that don’t support this specification treat collector as an unknown element. The controls inside it still work, and each is submitted as its own entry: areaCode=206&centralOfficeCode=555&lineNumber=0123. A server that accepts both forms works with both kinds of user agent.

2. The collector element

2.1. Element definition

Categories:
Flow content.
Phrasing content.
Listed, labelable, and submittable form-associated element.
Palpable content.
Contexts in which this element can be used:
Where phrasing content is expected.
Content model:
Phrasing content, but there must be no collector element descendants.
Content attributes:
Global attributes
disabled — Whether the collector and the controls inside it are disabled
form — Associates the element with a form element
name — Name of the element to use for form submission and in the form.elements API
pattern — Template that combines the collected controls' values
required — Whether the value is required for form submission
DOM interface:
HTMLCollectorElement

The collector element represents a single value made up of the values of the controls inside it, which are its collected controls.

The name, form, and disabled content attributes work as they do for other form-associated elements. A collector element is disabled if its disabled attribute is specified, or if it is a descendant of a disabled fieldset element and is not a descendant of that fieldset element’s first legend element child, if any.

The required attribute is a boolean attribute. When specified, the collector’s value is required. See § 3 Constraint validation.

Note: The collector element has no special rendering. It has no default styles, so it is display: inline, as it is in user agents that don’t support it. It needs no changes to the HTML parser.

2.2. Collectable elements

A collectable element is either:

  • an input element whose type attribute is in a state whose value mode is value; or

  • a select element that does not have a multiple attribute.

Note: The states whose value mode is value are Text, Search, Telephone, URL, Email, Password, Date, Month, Week, Time, Local Date and Time, Number, Range, and Color. Checkboxes, radio buttons, file uploads, and buttons are not collectable. select elements with a multiple attribute are excluded because they can hold more than one value.

The collector owner of an element element is the nearest ancestor of element that is a collector element, or null if there is no such ancestor.

The candidate controls of a collector element collector are the collectable elements whose collector owner is collector and whose form owner is collector’s form owner, in tree order.

Note: Because ancestors are found in the element’s own tree, controls in a shadow tree are never collected by a collector element outside it.

2.3. The pattern attribute

The pattern content attribute is a template that says how the values of the collected controls combine into the collector’s value. It is made up of literal text and placeholders. A placeholder is an identifier between U+007B ({) and U+007D (}), such as {areaCode}. It stands for the value of the control whose name attribute is that identifier.

To include a literal U+007B ({) or U+007D (}) in the collector’s value, authors write it twice: {{ or }}.

With an areaCode control whose value is 206:
pattern Value
({areaCode}) (206)
{{{areaCode}}} {206}
{{areaCode}}-{areaCode} {areaCode}-206
{areaCode}{areaCode} 206206

In {{{areaCode}}}, the first two braces are an escaped {, the next brace starts the placeholder, and the last two braces are an escaped }.

A pattern token is a struct with two items: a kind, which is either "literal" or "placeholder", and a text, which is a string.

To parse a collector pattern given a string input:

  1. Let tokens be an empty list.

  2. Let literal be the empty string.

  3. Let position be a position variable for input, initially pointing at the start of input.

  4. While position is not past the end of input:

    1. Let c be the code point at position within input.

    2. If c is U+007B ({) or U+007D (}), and the code point after position is also c, then append c to literal, advance position by 2, and continue.

    3. If c is U+007B ({), then:

      1. Let start be position.

      2. Advance position by 1.

      3. Let identifier be the result of collecting a sequence of code points that are neither U+007B ({) nor U+007D (}) from input, given position.

      4. If identifier is not the empty string, and position is not past the end of input, and the code point at position is U+007D (}), then:

        1. If literal is not the empty string, then append a new pattern token whose kind is "literal" and whose text is literal to tokens, and set literal to the empty string.

        2. Append a new pattern token whose kind is "placeholder" and whose text is identifier to tokens.

        3. Advance position by 1.

        4. Continue.

      5. Unmatched brace: Set position to start.

    4. Append c to literal, and advance position by 1. If c is U+007B ({) or U+007D (}), this is also an unmatched brace.

  5. If literal is not the empty string, then append a new pattern token whose kind is "literal" and whose text is literal to tokens.

  6. Return tokens.

If the pattern attribute is specified, its value must be a valid collector pattern: a string that, when parsed, never reaches an unmatched brace, and in which every placeholder’s identifier is identical to the value of the name attribute of one of the collector’s candidate controls.

Note: User agents are lenient with invalid patterns. A brace that is neither doubled nor part of a placeholder is kept as literal text. A placeholder whose identifier matches no control is replaced with nothing, and doesn’t stop the collector from being complete.

Note: Identifiers are compared exactly. { areaCode } does not match a control named areaCode.

2.4. Collected controls

The collected controls of a collector element collector are the list returned by these steps:

  1. Let candidates be collector’s candidate controls.

  2. If collector does not have a pattern attribute, then return candidates.

  3. Let tokens be the result of parsing the value of collector’s pattern attribute.

  4. Let result be an empty list.

  5. For each control of candidates:

    1. If control does not have a name attribute, then continue.

    2. Let name be the value of control’s name attribute.

    3. If tokens does not contain a pattern token whose kind is "placeholder" and whose text is name, then continue.

    4. If result already contains an element whose name attribute’s value is name, then continue.

    5. Append control to result.

  6. Return result.

An element is a collected control if it is one of the collected controls of its collector owner.

Note: A control inside a collector that the pattern doesn’t mention, such as a "Save this number" checkbox or a text field with a different name, is not a collected control. It behaves like any other control.

The collected value of a collected control control is:

  • the empty string, if control is disabled;

  • if control is a select element, the value of the first option element in control’s list of options whose selectedness is true and that is not disabled, or the empty string if there is no such option element;

  • otherwise, control’s value.

The enabled collected controls of a collector element are its collected controls that are not disabled.

A collector element is empty if the collected value of every one of its enabled collected controls is the empty string. It is complete if the collected value of every one of its enabled collected controls is not the empty string.

Note: A collector with no enabled collected controls is both empty and complete.

2.5. The collector’s value

The value of a collector element collector is the result of these steps:

  1. If collector is empty, then return the empty string.

  2. If collector does not have a pattern attribute, then return the concatenation of the collected values of collector’s collected controls, in order.

  3. Let result be the empty string.

  4. For each token of the result of parsing the value of collector’s pattern attribute:

    1. If token’s kind is "literal", then append token’s text to result.

    2. Otherwise, if collector’s collected controls contain an element whose name attribute’s value is token’s text, then append that element’s collected value to result.

  5. Return result.

Note: An empty collector’s value is the empty string, not the pattern’s literal text. An optional telephone number that the user leaves blank therefore submits phone=, not phone=() -.

Note: The collector fires no events of its own. The input and change events of its collected controls bubble through it, so authors can listen for them on the collector and read its value.

2.6. The DOM interface

[Exposed=Window]
interface HTMLCollectorElement : HTMLElement {
  [HTMLConstructor] constructor();

  [CEReactions, Reflect] attribute boolean disabled;
  readonly attribute HTMLFormElement? form;
  [CEReactions, Reflect] attribute DOMString name;
  [CEReactions, Reflect] attribute DOMString pattern;
  [CEReactions, Reflect] attribute boolean required;

  readonly attribute DOMString type;
  readonly attribute DOMString value;

  readonly attribute boolean willValidate;
  readonly attribute ValidityState validity;
  readonly attribute DOMString validationMessage;
  boolean checkValidity();
  boolean reportValidity();
  undefined setCustomValidity(DOMString error);

  readonly attribute NodeList labels;
};

The disabled, name, pattern, and required IDL attributes must reflect the content attributes of the same name.

The form IDL attribute returns the element’s form owner, as it does for other listed form-associated elements.

The type getter steps are to return "collector".

The value getter steps are to return this’s value.

The willValidate, validity, validationMessage, checkValidity(), reportValidity(), and setCustomValidity(error) members work as they do for other listed form-associated elements, as defined by the constraint validation API [HTML], with the additions in § 3 Constraint validation.

The labels IDL attribute returns the element’s label elements, as it does for other labelable elements.

const phone = document.getElementById("phone");

phone.value;                          // "(206) 555-0123"
phone.validity.patternMismatch;       // true while the pattern is only partly filled in
new FormData(phone.form).get("phone") // "(206) 555-0123"

// React to changes in any of the pieces.
phone.addEventListener("input", () => preview.textContent = phone.value);

// Feature detection.
const supported = "HTMLCollectorElement" in window;

3. Constraint validation

3.1. The collector’s constraints

A collector element is barred from constraint validation if it is disabled or has a datalist element ancestor.

A collector element that has a required attribute and is empty is suffering from being missing.

A collector element that is neither empty nor complete is suffering from a pattern mismatch.

Note: In other words, a collector is invalid while the user has filled in some parts of it and not others. An optional collector that is left entirely blank is valid.

A collector element whose custom validity error message is not the empty string is suffering from a custom error.

In addition, the collector rolls up the validity of its pieces: for each of a collector element’s enabled collected controls that is a candidate for constraint validation, the collector suffers from every validity state that control suffers from. For example, if a collected control is too short, the collector is suffering from being too short, and its tooShort flag is true.

Note: Each collected control keeps its own validity. Authors can put required, minlength, and pattern attributes on the pieces, and style them with :invalid. The collector’s validity is the rollup of all of them.

3.2. The problem control

The problem control of a collector element collector is the first element, in tree order, among collector’s enabled collected controls that is focusable and either has a collected value that is the empty string or is a candidate for constraint validation that does not satisfy its constraints. If there is no such element, it is the first focusable element among collector’s enabled collected controls. If there is no such element either, it is null.

3.3. The validation message

The validationMessage of a collector element collector that does not satisfy its constraints should be:

  1. collector’s custom validity error message, if that is not the empty string;

  2. otherwise, if collector is suffering from being missing or suffering from a pattern mismatch because of its own constraints, a message from the user agent saying that the whole value is needed, such as "Please fill out all parts of this field";

  3. otherwise, the validationMessage of the first of collector’s enabled collected controls, in tree order, that does not satisfy its constraints.

3.4. Reporting problems

When the user agent reports a problem with a collector element collector to the user, whether from reportValidity() or from interactively validate the constraints, it should:

  • show collector’s validationMessage, positioned near collector or its problem control; and

  • if collector’s problem control is not null, run the focusing steps for the problem control, instead of trying to focus collector.

3.5. Changes to statically validating the constraints

Because the collector rolls up the validity of its pieces, a form reports the collector, not each piece. The algorithm to statically validate the constraints of a form element [HTML] is changed as follows. Inserted text is marked like this .

  1. Let controls be a list of all the submittable elements whose form owner is form, in tree order.

  2. Let invalid controls be an initially empty list of elements.

  3. For each element field in controls, in tree order:

    1. If field is not a candidate for constraint validation, then move on to the next element.

    2. If field is a collected control, then move on to the next element.

    3. [Otherwise, if field satisfies its constraints, move on to the next element. This step and the rest of the algorithm are unchanged.]

Note: The invalid event therefore fires at the collector, and not at its collected controls, when a form is submitted. Calling checkValidity() on a collected control directly still fires invalid at that control.

3.6. User validity

A collector element’s user validity is true if at least one of its collected controls has a user validity of true, and either none of its collected controls is focused or every one of them has a user validity of true. Otherwise, it is false.

Note: This means :user-invalid matches the collector once the user has changed one of its pieces and then left the collector, or once a form submission has been attempted. It doesn’t match while the user is still moving through the pieces for the first time. Resetting the form resets the pieces, and so the collector.

The collector’s message and styles cover the whole value: 
<style>
  collector:user-invalid { outline: 2px solid crimson; }
  .error { display: none; color: crimson; }
  collector:user-invalid + .error { display: block; }
</style>

<label for="dob">Date of birth</label>
<collector id="dob" name="dob" pattern="{year}-{month}-{day}" required
           aria-describedby="dob-error">
  <input name="day" inputmode="numeric" minlength="2" maxlength="2" aria-label="Day">
  <select name="month" aria-label="Month">
    <option value="">Month</option>
    <option value="01">January</option>
    <!-- … -->
    <option value="12">December</option>
  </select>
  <input name="year" inputmode="numeric" minlength="4" maxlength="4" aria-label="Year">
</collector>
<p class="error" id="dob-error">Enter your full date of birth.</p>

The pieces appear in the order the user expects, and the value comes out in the order the server expects: dob=1990-07-04. The select element’s empty first option counts as an empty piece, so the collector isn’t complete until the user picks a month.

4. Form submission

4.1. Changes to constructing the entry list

The algorithm for constructing the entry list [HTML] is changed as follows. Inserted text is

marked like this . Steps that don’t change are summarized in brackets.

  1. For each element field in controls, in tree order:

    1. If any of the following are true, then continue:

      • [The existing conditions, such as field being disabled, are unchanged.]

      • field is a collected control.

    2. [If field is an Image Button, then append its coordinates and continue.]

    3. [If field is a form-associated custom element, then perform its entry construction algorithm and continue.]

    4. If either the field element does not have a name attribute specified, or its name attribute’s value is the empty string, then continue.

    5. Let name be the value of the field element’s name attribute.

    6. If field is a collector element, then create an entry with name and field’s value, append it to entry list, and continue.

    7. [The remaining steps are unchanged.]

Note: FormData’s constructor and the formdata event use the same algorithm. Scripts calling new FormData(form) therefore see the collector’s value, and none of its collected controls, exactly as the server does.

Note: A form with novalidate, or one submitted with submit(), skips validation. A collector that is only partly filled in then submits its partial value, such as (206) -, so that the server can tell it apart from a value the user left blank.

5. Changes to the HTML Standard

To integrate this specification into the HTML Standard [HTML], make these changes:

  1. Add § 2 The collector element as a new section in "Forms", after the fieldset element.

  2. Add collector to the lists of flow content, phrasing content, palpable content, form-associated elements, and listed, labelable, and submittable elements.

  3. In the definition of a disabled form control, add: "or it is a descendant of a collector element whose disabled attribute is specified".

  4. Apply the changes in § 3.5 Changes to statically validating the constraints and § 4.1 Changes to constructing the entry list.

  5. In interactively validate the constraints, add the requirements in § 3.4 Reporting problems.

  6. In "Pseudo-classes", add collector elements to the elements that :enabled, :disabled, :required, :optional, :valid, :invalid, :user-valid, and :user-invalid can match.

  7. In the label element, add: "If a label element’s labeled control is a collector element, the label element’s activation behavior should run the focusing steps for the first focusable element among the collector’s enabled collected controls."

  8. In the indices, add the collector element, its attributes, and the HTMLCollectorElement interface.

6. Accessibility considerations

  • A collector element maps to the group role [WAI-ARIA-1.2]. Its accessible name comes from its label elements, or from aria-label and aria-labelledby.

  • User agents should expose the collector as required when it has a required attribute, and as invalid when it matches :user-invalid.

  • Authors should still give each collected control its own accessible name, such as "Area code", because assistive technology announces the pieces one at a time as the user moves through them.

  • Showing one message for the whole value, and moving focus to the piece that needs attention, gives screen reader users one clear error instead of a separate announcement for every piece.

Define how collector maps to platform accessibility APIs in [HTML-AAM-1.0], including how the collector’s error message is exposed on its collected controls.

7. Security and privacy considerations

  • This specification exposes no new information. A collector’s value contains only the values of controls in the same document, which script can already read.

  • A collector only collects controls in its own tree with the same form owner. It can’t read controls in another document, such as a cross-origin iframe, or inside a shadow tree.

  • The pattern attribute is plain text substitution. It can’t run script, fetch resources, or evaluate expressions.

  • A collected control in the Password state still has its value combined into the collector’s value in the clear, as script could already combine it. Authors should avoid putting passwords in a collector.

8. More examples

This section is non-normative.

A select element can be a piece of the value. If the user types a number but hasn’t chosen a country yet, the collector is suffering from a pattern mismatch. 
<label for="mobile">Mobile number</label>
<collector id="mobile" name="mobile" pattern="+{country} {number}">
  <select name="country" autocomplete="tel-country-code" aria-label="Country code">
    <option value="">Country</option>
    <option value="1">United States (+1)</option>
    <option value="44">United Kingdom (+44)</option>
  </select>
  <input type="tel" name="number" autocomplete="tel-national" aria-label="Number">
</collector>

Choosing United Kingdom and typing 7700 900123 submits mobile=+44 7700 900123. Leaving both blank submits mobile=.

Without a pattern attribute, a collector joins all its collectable controls in tree order. The pieces don’t need names. 
<form action="/verify" method="post">
  <label for="code">Enter the 6-digit code we sent you</label>
  <collector id="code" name="code" required>
    <input maxlength="1" inputmode="numeric" autocomplete="one-time-code" aria-label="Digit 1">
    <input maxlength="1" inputmode="numeric" aria-label="Digit 2">
    <input maxlength="1" inputmode="numeric" aria-label="Digit 3">
    <input maxlength="1" inputmode="numeric" aria-label="Digit 4">
    <input maxlength="1" inputmode="numeric" aria-label="Digit 5">
    <input maxlength="1" inputmode="numeric" aria-label="Digit 6">
  </collector>
  <button>Verify</button>
</form>

The form submits code=482913. It can’t be submitted with only some of the digits.

Authors can replace the user agent’s message with their own, and check the whole value with script. 
const expiry = document.querySelector("collector[name=cc-exp]"); // pattern="{month}/{year}"

expiry.addEventListener("change", () => {
  const [month, year] = expiry.value.split("/").map(Number);
  const now = new Date();
  const expired = year + 2000 < now.getFullYear() ||
                  (year + 2000 === now.getFullYear() && month < now.getMonth() + 1);
  expiry.setCustomValidity(expired ? "This card has expired." : "");
});

9. Alternate proposals

This section is non-normative.

9.1. Linked form controls

Linked Form Controls takes a different approach to the same family of problems. It adds a link attribute to input and select elements that names the next control in a chain. Controls that are linked and share a name are submitted as one entry, with their values concatenated.

The two designs differ in these ways:

collector element link attribute
How pieces are grouped By containment in one element By ID references from each control to the next
Separators and ordering Any, through pattern None; values are joined in link order
Whole-value validation Yes, with a rollup error message No; each control is validated on its own
Focus moves as pieces fill No Yes, along with pasting and autofill spread across the pieces
Without support Each piece submitted under its own name Each piece submitted under the shared name

The designs don’t conflict. Collected controls could also be linked, so that a collector provides the value and validation and the links provide the editing behavior.

10. Open issues

Element name. The name collector needs checking against existing content that uses it as an unknown element. Alternatives include compound, fieldgroup, and composite.

Identifiers. Placeholders match the name attribute, so that a collector can be copied without ID clashes and so that user agents without support submit meaningful entries. Should they match id instead, or as well?

Setting the value. Should value be settable, or should there be a value content attribute, that splits a whole value into the pieces by matching it against the pattern? That would also let the user agent autofill a whole value, such as an autocomplete="tel" number, into the pieces. Adjacent placeholders such as {a}{b} can’t be split without extra information, such as each piece’s maxlength.

Moving focus. Should the user agent move focus to the next collected control when one fills up, and spread pasted text across the pieces?

More controls. Should textarea elements, checkboxes, radio buttons, and form-associated custom elements be collectable? Should a collector be allowed inside another and act as one of its pieces?

Validity flag. A partly filled collector reports patternMismatch. Would a new flag, such as incomplete, be clearer?

Unmatched placeholders. A placeholder that matches no control is silently replaced with nothing. Should the collector be invalid instead, so that authoring mistakes show up in testing?

Partial submission. When validation is skipped, should a partly filled collector submit its partial value, as specified, or the empty string?

Conformance

Conformance requirements are expressed with a combination of descriptive assertions and RFC 2119 terminology. The key words “MUST”, “MUST NOT”, “REQUIRED”, “SHALL”, “SHALL NOT”, “SHOULD”, “SHOULD NOT”, “RECOMMENDED”, “MAY”, and “OPTIONAL” in the normative parts of this document are to be interpreted as described in RFC 2119. However, for readability, these words do not appear in all uppercase letters in this specification.

All of the text of this specification is normative except sections explicitly marked as non-normative, examples, and notes. [RFC2119]

Examples in this specification are introduced with the words “for example” or are set apart from the normative text with class="example", like this:

Issues Index

Define how collector maps to platform accessibility APIs in [HTML-AAM-1.0], including how the collector’s error message is exposed on its collected controls. ↵
Element name. The name collector needs checking against existing content that uses it as an unknown element. Alternatives include compound, fieldgroup, and composite. ↵
Identifiers. Placeholders match the name attribute, so that a collector can be copied without ID clashes and so that user agents without support submit meaningful entries. Should they match id instead, or as well? ↵
Setting the value. Should value be settable, or should there be a value content attribute, that splits a whole value into the pieces by matching it against the pattern? That would also let the user agent autofill a whole value, such as an autocomplete="tel" number, into the pieces. Adjacent placeholders such as {a}{b} can’t be split without extra information, such as each piece’s maxlength. ↵
Moving focus. Should the user agent move focus to the next collected control when one fills up, and spread pasted text across the pieces? ↵
More controls. Should textarea elements, checkboxes, radio buttons, and form-associated custom elements be collectable? Should a collector be allowed inside another and act as one of its pieces? ↵
Validity flag. A partly filled collector reports patternMismatch. Would a new flag, such as incomplete, be clearer? ↵
Unmatched placeholders. A placeholder that matches no control is silently replaced with nothing. Should the collector be invalid instead, so that authoring mistakes show up in testing? ↵
Partial submission. When validation is skipped, should a partly filled collector submit its partial value, as specified, or the empty string? ↵
