Abstract

This specification extends HTML with three content attributes. The json attribute on a template element names a JSON resource for the template to load. The template attribute on any HTML element names a template, by its ID, to render into that element. The key attribute marks the elements in a template that receive data. The user agent makes one copy of the template for each item in the JSON data, and fills in each keyed element’s text and attributes from the item’s property with the same name, without script.

1. Introduction

This section is non-normative.

Many pages show a list of records: rows in a table, items in a list, options in a menu. When the records live in a JSON file, authors today write script that fetches the file, copies a template element once for each record, and fills in the copies. The script is similar on every page, and nothing appears when script is turned off or fails to load.

This specification lets authors declare the same thing in markup. The json attribute tells a template where its data is, the template attribute tells an element which template to render into itself, and the key attribute marks the elements in the template that receive data.

The file ./json/tableData.json contains: 
[
  { "city": "Seattle", "state": "Washington" },
  { "city": "Portland", "state": "Oregon" },
  { "city": "Boise", "state": "Idaho" }
]

The page contains:

<template id="tableRow" json="./json/tableData.json">
  <tr><td key="city"></td><td key="state"></td></tr>
</template>

<table>
  <thead>
    <tr><th>City</th><th>State</th></tr>
  </thead>
  <tbody template="tableRow">
    <tr><td colspan="2">Loading…</td></tr>
  </tbody>
</table>

When the file loads, the user agent replaces the contents of the tbody element with three rows. In each row, the td whose key is city holds that item’s city, and the one whose key is state holds its state:

<tbody template="tableRow">
  <tr><td key="city">Seattle</td><td key="state">Washington</td></tr>
  <tr><td key="city">Portland</td><td key="state">Oregon</td></tr>
  <tr><td key="city">Boise</td><td key="state">Idaho</td></tr>
</tbody>
A property whose value is an object sets attributes too. Its content property becomes the element’s text, and every other property sets the attribute with that name. 
[
  {
    "city":  "Seattle",
    "link":  { "href": "/wa/seattle", "content": "Details" },
    "photo": { "src": "seattle.jpg", "alt": "Seattle skyline" }
  }
]

<template id="cityRow" json="./json/cities.json">
  <tr>
    <td key="city"></td>
    <td><a key="link"></a></td>
    <td><img key="photo"></td>
  </tr>
</template>

<table>
  <tbody template="cityRow"></tbody>
</table>

renders:

<tbody template="cityRow">
  <tr>
    <td key="city">Seattle</td>
    <td><a key="link" href="/wa/seattle">Details</a></td>
    <td><img key="photo" src="seattle.jpg" alt="Seattle skyline"></td>
  </tr>
</tbody>

User agents that don’t support this specification ignore all three attributes and keep showing the element’s original contents, here the "Loading…" row. Authors can put a useful fallback there, such as a link to the data.

Note: In HTML syntax, a / at the end of a start tag has no effect on elements that aren’t void. <td key="city"/> is an ordinary start tag, and <tbody template="tableRow"/> doesn’t end the tbody element. The examples in this specification use explicit end tags.

2. The json attribute

2.1. The content attribute

The json content attribute can be specified on template elements. If present, its value must be a valid non-empty URL potentially surrounded by spaces that identifies a JSON resource.

Each template element has a JSON data, which is either null or a list. It is initially null.

Each template element has a JSON fetch controller, which is either null or a fetch controller. It is initially null.

2.2. The IDL attribute

partial interface HTMLTemplateElement {
  [CEReactions, ReflectURL] attribute USVString json;
};

The json IDL attribute must reflect the json content attribute, as a URL.

2.3. Loading the data

When a template element becomes connected or becomes disconnected, and when its json attribute is set, changed, or removed, the user agent must update the JSON data of the element.

To update the JSON data of a template element template:

  1. If template’s JSON fetch controller is not null, then abort it, and set template’s JSON fetch controller to null.

  2. Set template’s JSON data to null.

  3. If template is not connected, or it does not have a json attribute, then return.

  4. Let url be the result of encoding-parsing a URL given the value of template’s json attribute, relative to template’s node document.

  5. If url is failure, then queue an element task on the DOM manipulation task source given template to fire an event named error at template, and return.

  6. Let request be a new request whose URL is url, client is template’s node document’s relevant settings object, destination is "json", mode is "cors", and credentials mode is "same-origin".

  7. Set template’s JSON fetch controller to the result of fetching request, with processResponseConsumeBody set to the following steps given a response response and null, failure, or a byte sequence bodyBytes:

    1. Set template’s JSON fetch controller to null.

    2. If response is a network error, or its status is not an ok status, or bodyBytes is null or failure, then fire an event named error at template, and return.

    3. Let value be the result of parsing JSON bytes to an Infra value given bodyBytes. If this throws an exception, then fire an event named error at template, and return.

    4. If value is a list, then set template’s JSON data to value. Otherwise, set it to « value ».

    5. For each host of template’s template hosts, render host.

    6. Fire an event named load at template.

Note: A template loads its data once, however many elements render it. Moving a template to another place in the document loads the data again.

3. The template attribute

3.1. The content attribute

The template content attribute can be specified on any HTML element. If present, its value must be the ID of a template element in the same tree.

The referenced template of an element host is found by these steps:

  1. If host does not have a template attribute, or its value is the empty string, then return null.

  2. Let candidate be the first element, in tree order, among the descendants of host’s root whose ID is the value of host’s template attribute.

  3. If candidate is a template element, then return candidate. Otherwise, return null.

The template hosts of a template element template are the elements, in tree order, among the descendants of template’s root whose referenced template is template.

3.2. The IDL attribute

partial interface HTMLElement {
  [CEReactions, Reflect] attribute DOMString template;
};

The template IDL attribute must reflect the template content attribute.

4. The key attribute

4.1. The content attribute

The key content attribute can be specified on any HTML element. Its value is any string. It marks an element in a template’s template contents as the place where the item property with the same name is bound. Outside a template’s contents, and in copies that have already been rendered, the attribute has no effect.

Unlike IDs, keys don’t need to be unique. Every element in a copy whose key matches a property receives that property’s value.

4.2. The IDL attribute

partial interface HTMLElement {
  [CEReactions, Reflect] attribute DOMString key;
};

The key IDL attribute must reflect the key content attribute.

const template = document.getElementById("tableRow");
const tbody = document.querySelector("tbody");

template.json;                              // "https://example.com/json/tableData.json"
tbody.template;                             // "tableRow"
template.content.querySelector("td").key;   // "city"

template.addEventListener("load", () => console.log("rows rendered"));
template.addEventListener("error", () => console.log("data failed to load"));

// Feature detection.
const supported = "json" in HTMLTemplateElement.prototype;

5. Rendering

5.1. When to render

The user agent must queue an element task on the DOM manipulation task source given an element host to render host when either of these happens:

  • host becomes connected while it has a template attribute; or

  • host’s template attribute is set or changed while host is connected.

When a template element’s id attribute is set, changed, or removed while the element is connected, the user agent must queue an element task on the DOM manipulation task source given the element to render each of its template hosts.

5.2. Rendering a template

To render a template into an element host:

  1. Let template be host’s referenced template.

  2. If template is null, or template’s JSON data is null, then return.

  3. If host has an ancestor whose template attribute has the same value as host’s template attribute, then return.

  4. Let fragment be a new DocumentFragment whose node document is host’s node document.

  5. For each item of template’s JSON data:

    1. If item is not an ordered map, then continue.

    2. Let clone be the result of cloning template’s template contents, with document set to host’s node document and subtree set to true.

    3. Let keyed be a list of the elements among the descendants of clone that have a key attribute, in tree order.

    4. For each element of keyed:

      1. Let key be the value of element’s key attribute.

      2. If item[key] exists, then bind a value given element and item[key].

    5. Append clone to fragment.

  6. Replace all with fragment within host.

Note: The ancestor check stops a template that contains its own host from rendering forever. A template can contain hosts for other templates, and those render normally.

5.3. Binding values

To bind a value given an element element and an Infra value value:

  1. If element is a script element, or an element whose local name is script and whose namespace is the SVG namespace, then return.

  2. If value is not an ordered map, then bind text given element and value, and return.

  3. For each name → propertyValue of value:

    1. If name is "content", then bind text given element and propertyValue.

    2. Otherwise, bind an attribute given element, name, and propertyValue.

To bind text given an element element and an Infra value value:

  1. If value is a string, then string replace all with value within element.

  2. Otherwise, if value is a number, then string replace all with the result of ToString(value) within element.

  3. Otherwise, if value is true or false, then string replace all with "true" or "false" within element.

  4. Otherwise, if value is null, then string replace all with the empty string within element.

  5. Otherwise, value is a list or an ordered map. Do nothing.

To bind an attribute given an element element, a string name, and an Infra value value:

  1. If name is not a valid attribute local name, then return.

  2. If element is an HTML element and its node document is an HTML document, then set name to name, ASCII lowercased.

  3. If name starts with "on" or is "srcdoc", then return.

  4. If value is false or null, then remove an attribute by name given name and element, and return.

  5. If value is a list or an ordered map, then return.

  6. Let text be value if value is a string, the empty string if value is true, or the result of ToString(value) if value is a number.

  7. If the result of running the basic URL parser on text is not failure, and its scheme is "javascript", then return.

  8. Set an attribute value given element, name, and text.

How each value binds into <input key="field">:
Value of field Result
"Seattle" Text content Seattle
{ "value": "Seattle" } value="Seattle"
{ "maxlength": 3 } maxlength="3"
{ "required": true } required=""
{ "required": false } or { "required": null } No required attribute
{ "aria-invalid": "false" } aria-invalid="false"
{ "onclick": "…" } Ignored
{ "formaction": "javascript:…" } Ignored

Note: true and false map to the presence and absence of an attribute, which suits boolean attributes such as required, checked, and selected. Attributes that take the strings "true" and "false", such as aria-invalid, need string values.

Note: Values are inserted as text. A value such as "<b>Seattle</b>" appears as those characters, and is never parsed as markup.

6. Interaction with other features

This section is non-normative.

Fallback content

The host’s original children stay in place until the data loads. They also stay if the data fails to load, and in user agents without support.

Keys in the copies

Copies keep their key attributes, so authors can select and style them, for example with [key="city"].

IDs in the template

id attributes are copied unchanged. A template rendered more than once should not contain IDs, or the page will have duplicates.

Missing properties

If an item has no property for a key, that element keeps whatever the template gave it, such as placeholder text or default attributes.

Keyed elements inside keyed elements

Binding content to an element replaces its children, including any keyed elements inside it.

Several hosts

Any number of elements can name the same template. They share one request, and each gets its own copies.

Order in the document

A host can come before or after its template. Hosts render when the data arrives, and hosts added later render as soon as they are connected.

Tables and selects

template elements are allowed inside table and select elements, and the parser keeps tr, td, and option elements in a template’s contents, so rows and options can be templated directly.

Form controls

Copies are new elements, so binding value, checked, or selected sets what the control shows.

Custom elements

Custom elements in the copies are upgraded when the copies are inserted, as with any other inserted content.

Script

The load and error events on the template tell scripts when rendering finishes or fails. After rendering, the copies are ordinary DOM that scripts can change.

7. Changes to the HTML Standard

To integrate this specification into the HTML Standard [HTML], make these changes:

  1. In the template element:

    • Add json to the element’s content attributes.

    • Add the json IDL attribute to the HTMLTemplateElement interface.

    • Add the JSON data and JSON fetch controller concepts, and the update the JSON data algorithm and the conditions that run it.

  2. In global attributes, add template and key, and add the template and key IDL attributes to the HTMLElement interface.

  3. Add § 3.1 The content attribute, § 4.1 The content attribute, and § 5 Rendering as a new subsection after the template element.

  4. In the index of element attributes, add these rows:

    • attribute json; element template; description "JSON data to render the template with"; value "Valid non-empty URL potentially surrounded by spaces".

    • attribute template; elements "HTML elements"; description "Template to render into the element"; value "ID of a template element".

    • attribute key; elements "HTML elements"; description "Name of the data property bound to the element"; value "Text".

  5. In the index of events, add load and error as fired at template elements.

8. Accessibility considerations

Rendered content is ordinary DOM, so assistive technologies see the same table rows, list items, or options that any other page would have.

Because attributes can be bound, data can and should supply accessible names and descriptions, such as alt for images and aria-label for icon-only links. Templates should give these attributes a sensible default in case the data leaves them out.

Rendering replaces the host’s contents after the page has loaded, and assistive technologies might not announce the change. Authors can set aria-busy="true" on the host and remove it in a load event listener, or describe the loading state in the fallback content.

Fallback content should make sense on its own, because some users will only ever see it.

9. Security and privacy considerations

JSON data can come from a different party than the page, such as a third-party API or content that users submitted. Binding is designed so that data can fill in a template but cannot add behavior to it:

  • Text values are inserted as text and never parsed as markup.

  • Data can’t create elements. It can only change elements the author put in the template.

  • Event handler attributes, whose names start with on, are ignored.

  • srcdoc is ignored, because it would put markup from the data into an iframe with the page’s origin.

  • Values that are javascript: URLs are ignored for every attribute, so data can’t turn a link, form action, or frame into script.

  • script elements, in HTML and SVG, never receive values, so data can’t set a script’s source or text.

Some risks remain, and authors should consider them before binding data they don’t control:

  • A bound style attribute, or text bound into a style element, can change how the page looks, and CSS can be used to leak information.

  • A bound href or src can point anywhere other than a javascript: URL, including tracking pixels and phishing pages.

Loading the data:

  • The request uses CORS. A cross-origin resource must opt in with Access-Control-Allow-Origin, and credentials are sent only to the page’s own origin. The page learns nothing that fetch() couldn’t already tell it.

  • The request happens without script, like an image or a stylesheet. It reveals no more about the user than those requests do.

  • The request is subject to Content Security Policy like any other fetch. See § 12 Open issues for which directive applies.

10. More examples

This section is non-normative.

A team list with links and photos, and a fallback link for user agents without support. 
<template id="person" json="/team.json">
  <li>
    <img key="photo" src="/avatar.png" alt="">
    <a key="name"></a>, <span key="role"></span>
  </li>
</template>

<ul template="person">
  <li><a href="/team.json">View the team</a></li>
</ul>

[
  {
    "photo": { "src": "/ana.jpg", "alt": "Ana" },
    "name": { "href": "/team/ana", "content": "Ana" },
    "role": "Designer"
  }
]

The list becomes:

<li>
  <img key="photo" src="/ana.jpg" alt="Ana">
  <a key="name" href="/team/ana">Ana</a>, <span key="role">Designer</span>
</li>
Options for a select element, with a value that differs from the label, and one option selected. 
<template id="stateOption" json="/states.json">
  <option key="state"></option>
</template>

<label>State
  <select name="state" template="stateOption">
    <option>Loading…</option>
  </select>
</label>

[
  { "state": { "value": "OR", "content": "Oregon" } },
  { "state": { "value": "WA", "content": "Washington", "selected": true } }
]
Two hosts share one template, and so one request. A single object, rather than an array, renders once. 
<template id="summary" json="/stats.json">
  <span key="count"></span> cities
</template>

<p template="summary">…</p>
<footer template="summary">…</footer>

With {"count": 3}, both elements show "3 cities".

11. Alternate proposals

This section is non-normative.

11.1. Array of bindings (rejected)

Status: rejected. Each item would be an array of binding objects, each naming its element with a key property, instead of a map from keys to values:

[
  [
    { "key": "city",  "content": "Seattle" },
    { "key": "link",  "href": "/wa/seattle", "content": "Details" },
    { "key": "photo", "src": "seattle.jpg", "alt": "Seattle skyline" }
  ],
  [
    { "key": "city",  "content": "Portland" },
    { "key": "link",  "href": "/or/portland", "content": "Details" },
    { "key": "photo", "src": "portland.jpg", "alt": "Portland bridges" }
  ]
]

It renders the same rows as the second introduction example, but it was rejected because:

  • Every value needs a wrapper object, even plain text, so the data is longer.

  • The same key can appear twice in one row, so the specification would need a rule for which binding wins.

  • key becomes a reserved property name, so data couldn’t set a key attribute.

  • Data from APIs and spreadsheets is usually already a list of objects, so it would need converting first.

11.2. Script

Authors can already fetch the JSON, clone the template, and fill in the copies with script. It takes a dozen lines, has to be repeated or packaged for each page, and shows nothing when script is turned off or fails.

11.3. Template instantiation and DOM Parts

The Web Components community has discussed template instantiation and DOM Parts: script APIs that mark the parts of a template that change and update them efficiently. Those proposals serve frameworks that update the page many times. This specification covers the simpler case of rendering static data once, without script, and could later be built on top of DOM Parts.

11.4. A src attribute

The template could use src instead of json. The name json makes the expected format clear, and leaves room for other formats later.

12. Open issues

The content property. Because content means the element’s text, data can’t set a content attribute, such as the one on meta elements. Should the text use a name that can’t be an attribute, such as #text?

Attribute guards. Is a fixed list of ignored attributes and values enough, or should binding integrate with Trusted Types and the HTML Sanitizer API’s configuration?

Nested data. A property whose value is an array is ignored. Should a host inside a template render that array, for example the list of cities inside each state?

Part of the resource. Should authors be able to render part of the JSON, such as the cities property of the top-level object?

Refreshing and script-supplied data. Should there be a way to load the data again, such as a reload() method, or to give a template data from script?

Load event. Should loading the data delay the document’s load event, as images do?

Content Security Policy. Which directive governs these requests? connect-src matches fetch().

Attribute names. Are template and key safe as new global attributes and HTMLElement properties, given that some libraries and custom elements already use properties with those names?

The key words “MUST”, “MUST NOT”, “REQUIRED”, “SHALL”, “SHALL NOT”, “SHOULD”, “SHOULD NOT”, “RECOMMENDED”, “MAY”, and “OPTIONAL” in the normative parts of this document are to be interpreted as described in RFC 2119. However, for readability, these words do not appear in all uppercase letters in this specification.

All of the text of this specification is normative except sections explicitly marked as non-normative, examples, and notes. [RFC2119]

Examples in this specification are introduced with the words “for example” or are set apart from the normative text with class="example", like this:
